# 1️⃣ 학습 내용 정리

## 1. 인덱스 개념을 파악하자 

### 📖 인덱스란?
- **인덱스(Index)** = SELECT로 조회할 때 결과를 **빠르게** 찾을 수 있도록 도와주는 도구
> 비유: 책 뒤의 '찾아보기'
>>찾아보기가 없으면 → 첫 페이지부터 끝까지 넘겨봐야 함 (전체 테이블 검색)
>>찾아보기가 있으면 → 단어 옆 페이지 번호로 바로 이동
- 인덱스 유무에 따라 **결과값은 동일**하고, **속도만 달라짐**
- 데이터가 적을 땐 체감이 없지만, **대용량 테이블**일수록 성능 차이가 큼


### ⚖️ 인덱스의 장점과 단점

|  장점 |  단점 |
|---|---|
| SELECT 검색 속도가 매우 빨라짐 | 인덱스도 공간을 차지함 (대략 테이블 크기의 **10%** 추가 공간) |
| 컴퓨터 부담 감소 | 처음 인덱스를 만들 때 시간이 오래 걸릴 수 있음 |
| **전체 시스템 성능 향상** | **INSERT / UPDATE / DELETE**가 잦으면 오히려 성능이 나빠질 수 있음 |

> 💡 **인덱스가 있다고 무조건 좋은 것은 아니다!** 비타민도 적정량만 먹어야 몸에 좋은 것처럼, 필요한 곳에만 만들어야 함.  
> 인덱스를 써서 찾을지, 전체 테이블을 훑을지는 **MySQL이 알아서 판단**함.
### 🗂️ 인덱스의 종류

| 구분 | 클러스터형 인덱스 | 보조 인덱스 |
|---|---|---|
| 영문 | Clustered Index | Secondary Index |
| 관련 제약조건 | **기본 키(PRIMARY KEY)** | **고유 키(UNIQUE)** |
| 테이블당 개수 | **1개만** 가능 | **여러 개** 가능 |
| 정렬 | 지정한 열 기준으로 **자동 정렬** | **정렬되지 않음** |
| 비유 | 영어사전 (책 자체가 찾아보기) | 일반 책 뒤의 찾아보기 |

### 🤖 자동으로 생성되는 인덱스
- 인덱스는 **열(컬럼) 단위**로 생성됨 (보통 *하나의 열 = 하나의 인덱스*)
- `PRIMARY KEY` 지정 → **클러스터형 인덱스** 자동 생성
- `UNIQUE` 지정 → **보조 인덱스** 자동 생성

```sql
USE market_db;
CREATE TABLE table1 (
    col1 INT PRIMARY KEY,   -- 기본 키 → 클러스터형 인덱스
    col2 INT,
    col3 INT
);
SHOW INDEX FROM table1;
```

```sql
CREATE TABLE table2 (
    col1 INT PRIMARY KEY,   -- 클러스터형 인덱스
    col2 INT UNIQUE,        -- 보조 인덱스
    col3 INT UNIQUE         -- 보조 인덱스
);
SHOW INDEX FROM table2;
```

**🔍 `SHOW INDEX` 결과 읽는 법**

| 컬럼 | 의미 |
|---|---|
| `Key_name` | `PRIMARY`면 클러스터형 인덱스 / 열 이름(col2 등)이면 보조 인덱스 |
| `Column_name` | 인덱스가 만들어진 열 |
| `Non_unique` | `0` = 중복 불가(고유 인덱스), `1` = 중복 허용(단순 인덱스) |

> 📌 **고유 인덱스 vs 단순 인덱스**  
> - 고유 인덱스(Unique Index): 값이 중복되지 않음 → 기본 키·고유 키로 지정하면 생성  
> - 단순 인덱스(Non-Unique Index): 값이 중복되어도 됨 → 그 외의 인덱스

### 🔃 클러스터형 인덱스는 자동 정렬, 보조 인덱스는 정렬 X

**클러스터형 인덱스 (영어사전)**
```sql
-- 기본 키가 없는 상태 → 입력한 순서 그대로 저장
ALTER TABLE member
    ADD CONSTRAINT
    PRIMARY KEY (mem_id);     -- mem_id 기준으로 자동 정렬됨!
SELECT * FROM member;
```

```sql
-- 기본 키를 다른 열로 변경 → 해당 열 기준으로 재정렬 (영한사전 → 한영사전)
ALTER TABLE member DROP PRIMARY KEY;
ALTER TABLE member
    ADD CONSTRAINT
    PRIMARY KEY (mem_name);
```
- 이후 INSERT하는 데이터도 **알아서 기준에 맞춰 정렬**되어 들어감

**보조 인덱스 (책 뒤의 찾아보기)**
```sql
ALTER TABLE member
    ADD CONSTRAINT
    UNIQUE (mem_id);          -- 데이터 순서/내용은 변하지 않음
```
- 책 본문은 그대로 두고 **뒤에 찾아보기만 추가**하는 것과 같음
- 새 데이터는 **맨 뒤에 추가**됨
- 여러 개 만들 수 있지만, **만들 때마다 공간을 차지**하므로 꼭 필요한 열에만 만들기

> ⚠️ **기본 키 변경 시 주의점**  
> - 대용량 데이터가 있는 상태에서 기본 키를 지정하면 **재정렬 때문에 시간이 매우 오래 걸림**  
> - `mem_name`처럼 **중복될 수 있는 열**을 기본 키로 쓰면 논리적으로 위험함 (실습이라 가능했던 것)

<br>


> **확인문제: 다음은 인덱스 종류와 관련된 설명입니다. 가장 거리가 먼 것을 하나 고르세요.**

보기는 아래와 같습니다.
```
1️⃣ 클러스터형 인덱스는 영어사전과 비슷한 개념입니다.
2️⃣ 보조 인덱스는 일반 책의 찾아보기와 비슷한 개념입니다.
3️⃣ 클러스터형 인덱스는 기본 키를 설정하면 자동 생성됩니다.
4️⃣ 보조 인덱스는 NOT NULL을 설정하면 자동 생성됩니다.
```

```
정답: 4️⃣ 

이유:
- 보조 인덱스는 NOT NULL이 아니라 고유 키(UNIQUE)를 설정하면 자동으로 생성된다.
- NOT NULL은 NULL 값을 허용하지 않는 제약조건일 뿐, 인덱스 생성과는 관련이 없다.
```


## 2. 인덱스의 내부 작동 

### 🌳 균형 트리 (Balanced Tree, B-tree)
- 클러스터형·보조 인덱스 모두 **내부적으로 균형 트리**로 구성됨
- 나무를 거꾸로 뒤집은 형태의 자료구조

```
        [ 루트 노드 ]            ← 모든 검색의 시작점
        /     |     \
   [중간 노드] ...               ← 데이터가 많으면 단계가 늘어남
     /   \
 [리프 노드] [리프 노드]          ← 맨 마지막 노드
```

| 용어 | 설명 |
|---|---|
| **노드(Node)** | 데이터가 저장되는 공간 |
| **루트 노드** | 가장 상위 노드 (모든 출발점) |
| **중간 노드** | 루트와 리프 사이의 노드 |
| **리프 노드** | 가장 마지막 노드 |
| **페이지(Page)** | MySQL에서 노드를 부르는 이름. **최소 저장 단위, 16KB (16384 byte)** |

> 📌 데이터를 1건만 입력해도 **1페이지(16KB)** 가 필요함 (노트에 단어 1개만 적어도 1장이 필요한 것과 같음)

### 🔎 검색 원리: 전체 테이블 검색 vs 인덱스 검색

`MMM` 데이터를 찾는 예시 (리프 페이지 3개, 루트 페이지 1개)

| 구분 | 방식 | 읽은 페이지 수 |
|---|---|---|
| **전체 테이블 검색** (Full Table Scan) | 처음부터 끝까지 모든 페이지 검색 | **3페이지** |
| **인덱스 검색** (Index Scan) | 루트 페이지(AAA, FFF, LLL) → 세 번째 리프 페이지로 이동 | **2페이지** |

- 균형 트리는 **무조건 루트 페이지부터** 검색
- 데이터 건수가 아니라 **읽은 페이지 수**로 효율성을 판단
- 데이터가 많아질수록(단계가 많아질수록) 페이지 수 차이가 **훨씬 커짐**

### ✂️ 페이지 분할 (Page Split)
- **새로운 페이지를 준비해서 데이터를 나누는 작업**
- 인덱스가 있으면 INSERT가 느려지는 **핵심 이유**
- 페이지 분할이 자주 일어나면 MySQL 성능에 큰 영향을 줌

| 상황 | 예시 | 결과 |
|---|---|---|
| 빈 공간 있음 | `III` 입력 | `JJJ`가 한 칸 아래로 이동, `III` 삽입 → **순식간에 처리** |
| 빈 공간 없음 | `GGG` 입력 | 새 페이지 확보 → **페이지 분할 1회** → 루트 페이지에도 새 페이지 등록 |
| 루트도 꽉 참 | `PPP`, `QQQ` 연속 입력 | `QQQ` 입력 시 리프 분할 → 루트도 분할 → 기존 루트는 **중간 페이지**가 되고 새 루트 생성 |

> 😵 `QQQ` 하나를 입력하는데 **새 페이지 3개 할당 + 페이지 분할 2회** 발생!  
> → 인덱스가 있으면 데이터 변경(특히 INSERT) 작업은 오히려 느려질 수 있음

### 🏗️ 인덱스의 구조

```sql
-- 인덱스 없이 테이블 생성 후 데이터 입력 (입력한 순서 그대로 저장됨)
CREATE TABLE cluster (
    mem_id   CHAR(8),
    mem_name VARCHAR(10)
);
-- INSERT 10건 ... (TWC, BLK, WMN, OMY, GRL, ITZ, RED, APN, SPC, MMU)
```

**① 클러스터형 인덱스 구조**
```sql
ALTER TABLE cluster
    ADD CONSTRAINT
    PRIMARY KEY (mem_id);     -- mem_id 기준 오름차순 정렬 + 균형 트리 형성
```
- 먼저 **행 데이터를 지정한 열 기준으로 정렬** → 각 페이지의 첫 번째 값으로 루트 페이지를 구성
- **리프 페이지 = 데이터 페이지 (데이터 그 자체)**
- 데이터 페이지도 인덱스에 **포함**됨 (영어사전의 본문이 찾아보기의 일부인 것과 같음)

**② 보조 인덱스 구조**
```sql
ALTER TABLE second
    ADD CONSTRAINT
    UNIQUE (mem_id);          -- 데이터 페이지는 건드리지 않음!
```
- **별도의 공간**에 인덱스 페이지를 생성 (책 뒤에 찾아보기를 따로 만드는 것)
- 리프 페이지에는 정렬된 열 값 + 실제 데이터 위치(**페이지 번호 + #위치**)가 기록됨
  - 예: `APN → 1001+#4` (1001번 페이지의 4번째 행)

### 🆚 인덱스에서 데이터 검색하기 (SPC 회원 찾기)

| 구분 | 읽는 순서 | 읽은 페이지 수 |
|---|---|---|
| **클러스터형 인덱스** | 루트(100번) → 리프=데이터 페이지(1001번) | **2페이지** |
| **보조 인덱스** | 루트(10번) → 리프(200번) → 데이터 페이지(1002번) | **3페이지** |

> ✅ 두 인덱스 모두 검색이 빠르지만, **클러스터형 인덱스가 조금 더 빠름** (리프 페이지가 곧 데이터 페이지라서 한 단계를 덜 거침)

> **확인문제: 다음 설명에서 빈칸에 공통으로 들어갈 용어를 쓰시오.**

```
인덱스를 구성하게 되면 데이터의 변경 작업(INSERT, UPDATE, DELETE)시에 성능이 나빠지는 단점이 있습니다.  
특히 INSERT 작업이 일어날 때 더 느리게 입력될 수 있는데요, 이유는 (           ) 이라는 작업이 발생하기 때문입니다.  
(            ) 작업이 일어나면 MySQL이 느려지고 너무 자주 일어나면 성능에 큰 영향을 줍니다.
```

### 🛠️ 인덱스 생성 / 제거 문법

```sql
-- 인덱스 생성 (CREATE INDEX로 만든 인덱스는 '보조 인덱스')
CREATE [UNIQUE] INDEX 인덱스_이름
    ON 테이블_이름 (열_이름) [ASC | DESC];

-- 인덱스 제거
DROP INDEX 인덱스_이름 ON 테이블_이름;
```

| 옵션 | 설명 |
|---|---|
| `UNIQUE` | 중복 불가한 **고유 보조 인덱스** 생성 (생략하면 중복 허용 = **단순 보조 인덱스**) |
| `ASC` / `DESC` | 오름차순 / 내림차순 (기본은 ASC, DESC는 거의 안 씀) |

> 📌 **보조 인덱스의 종류**: 단순 보조 인덱스(중복 허용, `CREATE INDEX`) / 고유 보조 인덱스(중복 불허, `CREATE UNIQUE INDEX`)  
> ⚠️ 기본 키·고유 키로 **자동 생성된 인덱스는 `DROP INDEX`로 제거 불가** → `ALTER TABLE`로 제거해야 함

DROP TABLE IF EXISTS employees;

CREATE TABLE employees (
    emp_id INT PRIMARY KEY,
    name VARCHAR(20),
    department VARCHAR(30),
    salary INT,
    hire_date DATE
);

INSERT INTO employees VALUES
